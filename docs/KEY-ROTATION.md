# Переход на новый ключ через 1.0.4

## Цепочка

`1.0–1.0.3 (старый ключ) → 1.0.4 (старый ключ) → 1.1+ (новый ключ + signing lineage)`.

Мост основан на стабильной 1.0.3, versionCode 7. Его интерфейс не заменяется интерфейсом 1.1. Старый приватный ключ нужен для выпуска 1.0.4 и однократного формирования доказательства ротации. Простого сертификата нового ключа в ресурсах APK недостаточно.

Android поддерживает APK Signature Scheme v3 и проверяемую ротацию начиная с API 28. APK 1.1+ подписывается с `--lineage` и `--rotation-min-sdk-version 28`, чтобы новый сертификат использовался и на Android 9–12, а не только на Android 13+. Сам установщик Android всегда проверяет подпись/полномочия ротации; preflight обновлятора не заменяет его.

Обновлятор принимает точное совпадение подписантов или продолжение платформенно проверенной истории одного подписанта вперёд. Обратная ротация, чужая история, дубликаты и смена multiple-signer набора отвергаются. Для прошивок, возвращающих только старое представление установленного сертификата, этот текущий сертификат должен быть в проверенной истории кандидата до нового сертификата.

## Создание настоящего ключа — только на Mac владельца

После применения исходников, из `~/free-my-tv/free-my-tv`:

```bash
python3 tools/signing.py init
```

Скрипт проверяет SHA-256 старого сертификата (`50aa9806…5b72c88`), создаёт RSA-4096 PKCS12, случайный пароль, signing lineage и локальную конфигурацию. Новый ключ и пароль не отправляются в GitHub. По умолчанию старый пароль `freemytv`; если он менялся, можно передать `--legacy-password-file /path/to/file`.

Материалы находятся в `~/.local/share/tvos-signing`, папка 0700, ключи/пароли 0600. В проекте остаётся игнорируемый `signing.local.json` с путём к папке. Сделайте защищённую резервную копию всей папки. Повторная инициализация не перезаписывает существующие ключи. Исходный freemytv.keystore из папки проекта переносится в защищённую папку как legacy-original.keystore после успешного создания lineage и конфигурации. Дополнительно там остаётся рабочая копия legacy.keystore. Если явно указан ключ вне проекта, он не перемещается.

Сборка версии 1.0.4 выбирает legacy-ключ; остальные версии выбирают новый ключ и lineage. Обычная сборка больше не создаёт ключ молча. Одноразовый ключ CI включается только через `CI=true TVOS_SIGNING_MODE=ci` и никогда не выпускается для пользователей.

## Два канала OTA

- Старые бинарные версии продолжают читать `/releases/latest/download/update.json`. GitHub Latest после публикации моста должен оставаться **v1.0.4**.
- Мост и 1.1+ читают `/releases/download/ota-v1/update.json`. Манифест указывает на APK конкретного версионного релиза, например `v1.1`.
- `ota-v1` — отдельный prerelease, всегда не Latest. Его первый манифест — 1.0.4 (мост видит, что версия актуальна), следующий — 1.1.
- Все релизы 1.1+ публикуются с `make_latest=false`. Если вручную сделать 1.1 Latest, старый канал тоже увидит 1.1: старый уже установленный бинарный клиент нельзя перепрограммировать изменением сервера GitHub.

Эта схема управляет предложениями OTA. Она не запрещает пользователю вручную скачать и установить совместимый APK с доказательством ротации.

## Порядок выпуска

1. На ветке `release-1.0.4` собрать `./release.sh 1.0.4`. Подпись должна совпасть со стабильной 1.0.3, versionCode 7.
2. `python3 tools/publish-release.py` создаёт draft. Проверить его APK/метаданные и цепочку установки на тестовом ТВ/эмуляторе.
3. `python3 tools/publish-release.py --publish` публикует мост как Latest и инициализирует ota-v1 его манифестом.
4. После проверки собрать стабильную 1.1 из ветки разработки с новым ключом и lineage. VersionCode должен быть выше 7 и всех ранее выданных dev-APK.
5. Теми же командами создать draft 1.1, затем опубликовать: helper ставит Latest=false и обновляет ota-v1. Он требует, чтобы legacy Latest оставался v1.0.4.

Не использовать прежние инструкции «каждый новый релиз делаем Latest». Не публиковать APK, подписанный одноразовым CI-ключом.

## Что подтверждают проверки

JVM-регрессии проверяют политику сертификатов и каналов, а CI создаёт одноразовые старый/новый ключи, реальный lineage и проверяет подписи новым сертификатом на API 28/30/33/34 через apksigner. Это не заменяет установку `1.0.3 → 1.0.4 → 1.1` на реальном Android, включая сохранение данных и работу OTA. До неё выпуск не считается проверенным.
